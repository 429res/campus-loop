- 抽屉复用 `LoopSheet` 的可中断动效、Escape、焦点圈定与返回；手机布局、深浅色、减少动态及滤镜降级继承公共 token 和材质。

## 当前契约与剩余接入

接口的严格字段、状态和恢复语义以 [API 契约](api-contract.md)、[A-03](a03-exchange-transaction.md)、[B-03.2](b03-invitation-rules.md)、[A-04](a04-exchange-expiry.md) 和 [B-04](b04-exchange-handoff.md) 为准。原先向 A/B 提出的创建与邀请契约已落地，后续 D-03 应按以下现有约定接入并验证：

1. 创建为 `POST /api/exchanges`，严格 body `{ruleVersion,idempotencyKey,flows:[{itemId,itemVersion,demandId,demandVersion},...]}`。使用同一推荐快照的物品/需求版本；缺版本先刷新，不填 0。同一逻辑提交保持同一键与请求，响应不确定时精确重放可返回原交换，不生成新键重复创建。
2. 本人分页为 `GET /api/exchanges/mine`，参与者详情为 `GET /api/exchanges/{id}`；仅展示服务端的 `status/version/allowedActions`、持久流向、参与者确认状态和 UTC 时间。非参与者（包括 ADMIN）读取或执行生命周期操作均为 404，不以管理员身份代办。
3. 确认为 `POST /api/exchanges/{id}/confirm` 的 `{version}`，取消为 `/cancel` 的 `{version,reason}`。409 保留原选择、原因和版本，回读后由用户决定；不能静默替换版本重试。已知交换 ID 用详情回读，不把网络失败当作取消成功。
4. 本地审查切片中的 A-04 以数据库 UTC 处理超时；客户端倒计时不修改交换状态。B-04 的 `/handoff` 接收 `{version,kind,acknowledged:true,note?}`，`/dispute` 接收 `{version,reason}`；按服务端允许动作及真实交接事实显示。正式交接、争议登记和倒计时均尚未接入 D 页面。
5. 事务锁序、唯一占用、幂等、条件释放与所有权流转由后端统一规则负责，D 不复制状态机。后端数据库证据与 D 的浏览器/微信交互验收分开记录。

双方/三方从推荐创建、邀请确认、交接完成及刷新/冲突恢复尚未通过 D 页面验收。当前阶段二前端仍未完成，不能以已存在的接口或后端测试代替实际页面闭环。

## 已修复的问题

| 严重性 | 原表现与影响 | 修复及回归 |
| --- | --- | --- |
| P1 | 同一需求能使用不同物品进入两份进行中交换；交接要求唯一需求引用，导致两份交换都无法正常完成 | 需求锁内拒绝重复使用，幂等重放优先；推荐与创建输入同步排除忙需求。测试并发只有一个成功、未选需求可用、取消恢复候选及推荐无写入 |
| P2 | 物品或需求版本用尽后仍可创建，后续取消/流转/关闭需求无法递增版本，交换被卡住 | 创建前给物品留两次、需求留一次递增余量。测试拒绝时逐表无写、最后安全版本可取消及完整完成 |
| P2 | 每轮先取固定最旧一批再跳过忙锁，最旧记录持续持锁时后面的过期交换一直无法回收 | 短事务候选查询在批次截断前跳过忙行，正式处理仍重锁重验。MySQL 测试批次为 1，后续交换先回收，解锁后首条也仅回收一次 |
| P2 | 推荐请求返回 401 时请求层先清 token，页面把当前失败当成旧响应忽略，持续加载 | 区分当前会话被清除的 401 和已过时请求，恢复登录提示；旧账号、旧请求仍不能覆盖当前状态 |
| P2 | 我的交换直接读取存储，没有随页面再次显示更新登录状态 | 用响应式状态和 onShow 刷新，覆盖登录返回/退出后页面显示 |
| P2 | 页面与验收脚本继续声称交换 API 为 501、发布后立即公开，与已交付后端冲突 | 页面说明前端接入进度；烟测检查空创建 400、待审私有→审核后公开，并保留会话清理 |

未修改 V1–V11 既有迁移、匹配评分/排序、交换截止规则或可信度等级。需求可选范围与版本业务边界已同步 API 契约。

# B-02：独立需求接入与可解释匹配

基础：main `aa31ab0` 已合入 B-01（PR #4），当前需求为 V4 的 cl_demand/cl_demand_item。需求状态 ACTIVE/INACTIVE/DELETED，删除保留墓碑；关联复用原物品。B-02 不改迁移，不创建交换或占用。任务分支 `feature/b02-independent-matching`；规则协调见 [Issue #7](https://github.com/429res/campus-loop/issues/7)。

## 已确定的边界

- 分类是硬条件；标签仅参与排序，延续每流向最多4个命中、60–100评分及原稳定排序。requiredTags 和最低成色不启用、不新增字段。
- 有向边 A→B 是 A 的物品满足 B 的需求；每环2/3人、每人提供一件、用户和物品都唯一。
- 需求只有ACTIVE可用；物品必须AVAILABLE、用户ACTIVE、没有 cl_item_hold 行，关联的当前物品owner必须仍是需求owner。INACTIVE/DELETED、无可提供物品、无关联或归属已转移不能凭旧关联组成独立需求环。
- 读取不修改物品、需求、交换和占用，不用FOR UPDATE。多表输入使用一个只读REPEATABLE_READ快照。
- 先检查全体AVAILABLE、有效用户且无占用物品的200件上限，再筛独立需求，不能以无本人物品等条件绕过上限。超过200返回422，不截取前200假装完整。独立快照最多20000行有效需求关联，读取第20001行即422；最多1000个推荐、全响应流向的matchedDemandIds累计最多20000项，超出任一项整次422。这些是新增且明确的资源保护，不会静默丢弃需求、截断方案或返回部分结果。

## 本分支的接入策略与确认状态

分类硬匹配、标签排序与不启用新硬条件来自本次任务的明确要求。以下兼容、选择和展示方案已在 Issue #7 通知 A/D，并作为本分支实现选型；尚未收到 D-02 消费确认，交付PR保持草稿，不把实施记录冒称团队已确认。仅在运行本功能分支后可调用，尚未合入main：

1. 旧公开 GET /api/matches 继续只使用物品上的 wantedCategoryId/wantedTags。新增需登录 GET /api/matches/independent，只返回包含当前用户的环，只用独立有效需求，不回退/混入旧字段。现有演示和前端保持原入口，D-02明确选择新入口。
2. 每条流向只考虑接收者在该环提供的物品所关联的有效需求。同一流向命中多条需求时只选标签计分贡献 min(命中数,4) 最大、同贡献下ID最小的一条用于计分和理由；其他命中需求ID按升序列出。不同需求的标签不并集加分；一个物品有向环只返回一次。
3. 新结果使用 data={ruleVersion:"independent-v2",recommendations:[...]}，空结果也带版本，每个推荐携带同版本。保留最小物品ID旋转规范化和现有字典序排序，推荐ID包含规则版本前缀。不支持的ruleVersion返回400，不隐式选用旧规则。
4. 新流向输出 demandId、matchedDemandIds、matchedCategoryId/Name、matchedTags、物品/用户流向和reason。不暴露需求description、未命中偏好标签或无关用户的需求列表；仅返回含当前用户的环。

影响：若改成旧入口默认切换，现有无独立需求的演示用户可能得到空结果；若混合/自动回退，停用独立需求可能被旧字段重新“激活”。多需求按并集计分会放大评分，按组合展开会制造重复物品环。本分支用显式新入口与固定规则版本避免这些隐式行为；是否接入D-02用户页面及将来是否退出旧入口仍须消费端确认。

## 给 D-02 的调用和虚构样例

使用现有登录请求封装调用 `GET /api/matches/independent`，或显式传 `?ruleVersion=independent-v2`。只允许一个ruleVersion参数；ownerId、requiredTags、minimumConditionLevel、重复ruleVersion等参数均400。保持现有 `GET /api/matches` 用于旧推荐；将独立版本传给旧入口会400，不会悄悄用旧字段返回结果。

完整JSON在 [b02-matching-responses.json](examples/b02-matching-responses.json)。两方/三方/停用无结果的成功响应由本分支实际纯模块生成，生成时断言方案数、分数、选中需求和方向；ID、姓名和物品全部虚构。422样例为服务端已有候选上限的统一错误结构，不能作为200成功处理。

**两方**：叶同学101提供教材11，蓝同学102提供音箱22。叶需求501想要数码且关联教材11；蓝需求502/503/504均想要教材且关联音箱22，偏好分别是“教材”“轻便”“教材+轻便”。叶还有未被本方案满足的绿植需求505，因此说明只能称每人至少一条需求满足。

| 提供物品与流向 | 选中需求 | 所有命中需求 | 选中需求命中标签 | 计分贡献 |
| --- | --- | --- | --- | --- |
| 教材11：叶101 → 蓝102 | 504 | 502、503、504 | 教材、轻便 | 2 |
| 音箱22：蓝102 → 叶101 | 501 | 501 | 便携 | 1 |

只返回 `independent-v2:cycle-11-22` 一次，分数75。界面显示服务端reason、选中需求编号与“另有2条需求可满足”，不要为502/503再复制两张同物品方案卡，也不要把三个需求标签叠加计分。

**三方**（另一组独立场景，ID可复用但数据不能与两方样例混合）：叶提供教材11且需求501想要运动；蓝提供音箱22且需求502想要教材；月提供球拍33且需求503想要数码，三条需求各关联本人提供物品。

| 提供物品与流向 | 选中需求 | 命中标签 |
| --- | --- | --- |
| 教材11：叶101 → 蓝102 | 502 | 教材 |
| 音箱22：蓝102 → 月103 | 503 | 便携 |
| 球拍33：月103 → 叶101 | 501 | 运动 |

月103调用也得到 `independent-v2:cycle-11-22-33`，分数70；展示顺序是规范化物品ID起点，不表示当前用户必须显示在第一位。反向三环如果成立，会有不同ID，不能按参与者集合将它误合并。

**无结果**：将三方场景需求501停用，返回如下真实空结果。不要自动换到旧入口补充推荐，否则用户会误以为已停用的需求仍有效。

```json
{"code":200,"msg":"成功","data":{"ruleVersion":"independent-v2","recommendations":[]}}
```

**超限**：201件可交换候选返回如下错误；有效需求关联超过20000、方案超过1000或理由ID累计超过20000也分别返回422和对应msg。所有超限响应都不包含部分推荐；展示服务端错误并说明当前范围超限，不能渲染成“暂无匹配”。当前尚无候选分页接口，不发送未经支持的page/categoryId参数，也不提示用户已能通过页面筛选解除上限。

```json
{"code":422,"msg":"初版匹配支持最多 200 件可交换物品；请先实现候选分区","data":null}
```

401按现有会话失效流程处理；400表示参数或规则版本不支持，保留页面并显示msg。推荐是读取时快照，不保证下一刻仍可交换；页面只能展示流向和理由，正式交换入口仍为后续。他人的需求ID只用于解释，不能据此访问仅本人可读的GET /demands/{id}详情。需求的编辑version与推荐ruleVersion不是同一个字段，不能拿其中任何一个当作物品占用凭证。
